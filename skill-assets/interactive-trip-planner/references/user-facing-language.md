## 核心原则

旅行者只需要理解旅行本身：为什么去、怎么走、会不会累、需要预约什么、改动会产生什么影响。开发语言、数据结构和渲染方式只留在代码与开发文档中。

所有聊天回复、地图标题、筛选、按钮、状态、提示、错误信息和最终交付使用自然语言。少量必要英文名称可以保留，例如酒店、餐厅、景点原名。

## 语言跟随

默认让攻略和地图跟随用户当前主要对话语言，不要求用户额外选择：

1. 用户明确指定输出语言时，始终以用户明确指定为准。
2. 用户没有指定时，跟随当前主要对话语言；判断最近几轮有实质内容的用户表达，不因一个地点英文名或短句临时切换整张地图。
3. 用户使用简体中文时，聊天、攻略和地图主体使用简体中文；使用繁体中文时尽量使用繁体中文；使用英语时使用英语。
4. 用户明确要求双语时，先确定主语言。按钮、状态和路线说明只使用主语言，地点标题可以使用“主语言名称 + 地点原名”，避免界面重复和拥挤。
5. 搜索和资料来源可以使用中文、英语和当地语言，但最终解释必须转成用户语言，不能把来源语言直接倾倒给用户。
6. 动态地图把主语言写入旅行数据（公开母版为 `PUBLIC_TRIP_DATA.trip.language`）并同步 HTML 页面语言；不能只翻译固定按钮，却让数据生成的地点标题继续回退为来源语言。

语言跟随覆盖所有用户可见内容：

- 对话中的旅行设计提案、选择理由和取舍。
- 地图标题、城市与日期、每日主题和路线说明。
- 地点分类、优先级、筛选、按钮、状态和错误提示。
- “为什么去”“怎么安排”“注意事项”等地点详情。
- 修改汇总、确认提示、复制反馈和地图生成的 Codex 请求。
- 最终交付说明、资料复核状态和需要临近确认的事项。

### 地点名称

- 有通行译名的国家、城市、区域和著名景点必须优先使用用户语言名称，不得因为来源页面使用英语或当地语言就直接沿用来源语言。
- 在中文攻略中，首次出现使用“译名（地点原名）”，例如“日惹（Yogyakarta）”“婆罗浮屠（Borobudur）”“圣家堂（Sagrada Família）”；后续日期标题、路线和筛选中只使用译名。
- 在英语攻略中使用英语通行名称；如果当地正式名称对现场识别有帮助，首次出现时补充当地名称。
- 酒店、餐厅、酒吧、商店和品牌保留地点原名，不强行翻译注册名称；可以在名称后用用户语言补充“酒店、餐厅、酒吧”等类型。
- 没有可靠译名时保留地点原名，并在同一句中用用户语言解释它是什么、位于哪里；不要自行发明生硬音译。
- 外部地图查询、官网、预约入口和内部别名保留地点原名或正式名称，保证搜索和现场识别。
- 地图数据中保留正式原名字段，并为当前主语言准备独立显示名；中文界面以中文显示名为主标题、正式原名为副标题。生成或验证中文地图时，应抽查著名景点并检查主要用户可见地点是否缺少中文显示名。

中文行程示例：

```text
9 月 1 日：北京出发，飞往日惹（Yogyakarta）。
9 月 3 日：婆罗浮屠（Borobudur）、周边村落与手工艺。
9 月 4 日：日惹城市生活、普兰巴南（Prambanan）和晚间表演。
9 月 9 日：飞往纳闽巴霍（Labuan Bajo），安排海港与日落。
9 月 10-11 日：科莫多（Komodo）两天一夜船程。
```

同一份攻略后续再次出现这些地点时，只写“日惹、婆罗浮屠、普兰巴南、纳闽巴霍、科莫多”。

### 日期和页面语言

- 日期、星期、数字和时间表达尽量符合用户语言习惯；不要在中文地图中混用英文月份和中文日期卡片。
- HTML 的页面语言标记应与地图主语言一致，方便浏览器、辅助功能和字体选择。
- 更新旧地图语言时，检查标题、路线、详情、按钮、提示和修改请求，不能只翻译导航栏而留下大段混合语言内容。

## 用户需要理解什么

每一段信息优先回答：

1. 这是什么。
2. 为什么值得或为什么这样安排。
3. 对路线、体力、预算或预约有什么影响。
4. 用户现在可以做什么。

不要用技术实现代替解释。例如，不说“状态已写入 localStorage”，而说“地图已经记住你的选择，刷新后仍会保留”。

## 推荐用词

| 内部或开发用词 | 给旅行者看的表达 |
|---|---|
| POI | 地点 |
| itinerary | 行程、每日路线 |
| candidate | 当天备选、顺路备选 |
| unassigned | 尚未安排行程 |
| draft | 需要重新安排 |
| reroute | 重新检查路线、重新安排当天行程 |
| route anchor | 主锚点、当天最重要的地点 |
| resource drawer | 地点详情、图片与相关链接 |
| change set | 我的修改、这次调整 |
| export | 请 Codex 重新安排 |
| localStorage | 地图已经记住你的选择 |
| state restore | 恢复上次浏览和选择 |
| renderer | 不展示；直接呈现地图 |
| themeProfile | 地图气质、视觉方向 |
| design token | 不展示；在开发文档中说明 |
| JSON / schema / hash | 不展示 |

“酒店”“餐厅”“市场”“博物馆”等旅行者熟悉的类别直接使用，不需要解释为数据分类。

## 对话写法

用旅行叙事组织内容，不描述 skill 正在执行哪个门或哪个步骤。

推荐：

```text
我先确认几项会改变路线的信息，再给你一版完整的旅行设计提案。你会先看到旅行主线、经过地点、酒店和吃饭逻辑；确认后我再制作地图。
```

避免：

```text
接下来执行主题确认门和 Design Language Pass，然后生成 POI schema 与 renderer。
```

用户已经给出明确偏好时，直接归纳，不强迫用户重新选择：

```text
你已经明确想看里斯本的街区生活，也想留出海上体验。我暂定用“山城日常 + 大西洋回声”作为双主线：里斯本负责旧城和吃喝，海岛段负责观鲸与放松。
```

## 地图写法

地图中的状态必须说明旅行意义：

- `必去`：这趟旅行的核心体验。
- `优先去`：很值得，尽量排入路线。
- `顺路可去`：路线允许时加入，不为它绕路。
- `当天备选`：适合替换或补充当天安排。
- `尚未安排行程`：已保留地点，但还没有放进某一天。
- `需要重新安排`：用户刚做了修改，正式路线尚未重新检查。
- `已预约`：时间已经确定，会影响当天其他安排。

按钮用动作结果命名：

- `加入这一天`
- `移出这一天`
- `换到其他日期`
- `查看地点详情`
- `查看图片与链接`
- `预览路线变化`
- `请 Codex 重新安排`
- `复制给 Codex`

不要用“资源”“操作”“提交”“同步状态”等模糊系统词作为主要按钮。

## 修改反馈

修改后不弹出技术提示。先让用户继续浏览，再用固定区域汇总：

```text
你调整了 3 个地点，影响 3 月 6 日和 3 月 7 日。
3 月 6 日新增两个地点后可能偏满；3 月 7 日移除一个地点后会更轻松。
```

整理后的内容包含：

- 新加入哪些地点、加入哪一天。
- 移除了哪些地点。
- 哪些地点改成必去、优先去或顺路可去。
- 哪几天需要重新检查。
- 可能的过满、折返、跨区或预约冲突。
- 下一步可以请 Codex 重新安排。
- 复制成功后明确提示“已复制，回到 Codex 对话发送即可”；失败时说明可以手动选择文字复制。

结构化修改数据可以保存在页面内部，但不得作为用户的主要阅读内容。

## 检查清单

- 页面是否出现 `POI`、`renderer`、`localStorage`、`themeProfile`、`JSON`、`schema`、`hash` 等开发词。
- 用户是否能看懂每个状态与旅行安排的关系。
- 按钮是否说明点击后会发生什么。
- 修改后是否说明影响日期和下一步。
- 错误提示是否告诉用户如何恢复，而不是只显示技术错误。
- 原名和必要英文是否服务地点识别，而不是替代中文解释。
- 地图主体语言是否跟随用户当前对话或明确指定语言。
- 简体、繁体或英语是否在标题、按钮、日期、地点详情和修改请求中保持一致。
- 地点原名是否保留到足以支持官网查询、地图搜索和现场识别。
- 有通行译名的地名是否已经转换成用户语言，而不是直接复制英文来源。
- 同一个地点是否只在首次出现时补原名，避免每日路线反复中英并列。
