# 目的地设计语言

本文件只在 Core 地图已经可以运行，或攻略已有明确设计系统时加载。默认先通过总览、某一天、地点详情、修改、撤销和重新安排的浏览器验收，再深化目的地设计语言。

设计语言不是换一组颜色，而是把目的地气质、信息层级和组件风格变成可复用规则。视觉实现不能阻塞 Core 交付，也不能改变行程状态语义。

设计语言由 Agent 根据旅行主题和目的地研究完成。除非视觉方向会明显改变地图使用方式，不要求旅行者理解或选择字体、token、renderer 等技术选项；对用户只说明地图会呈现怎样的旅行气质。

## 输出文件

进入 Visual 阶段的攻略包含：

- `docs/design-language.md`：解释设计方向、元素来源、组件规则和禁用项。
- `data/design-tokens.json`：给 HTML 使用的结构化 tokens。
- 公开母版单文件 HTML 的 `<style>`：只调整 design token 和组件外观，不改直接复制版的布局层级与交互结构。

## UI theme 与旅行主题的关系

旅行叙事主题回答“这趟旅行体验什么”，taste model 回答“按什么品味选点和安排节奏”，UI theme 只回答“同一份地图怎样呈现”。三者可以组合，不能互相替代。已有攻略级 `design-language.md` 和 `design-tokens.json` 仍是目的地视觉事实层；需要复用完整组件语言时，先读取 `assets/themes/index.json`，选择一个兼容当前 Core 的 UI theme，再用目的地 preset 生成攻略自己的 token 快照和 CSS override。未命中合适 preset 时沿用本节流程自行设计，不按 registry 顺序兜底。

## 设计流程

1. 视觉研究
   查找目的地相关的视觉线索：建筑、街区材质、交通系统、地图/导视、博物馆/酒店/餐厅/酒吧视觉、海报、菜单、票据、传统图案、自然地貌和当地摄影。

2. 选择 1 个主设计方向
   用 3-5 个关键词描述气质，例如“热带现代主义、克制旅行手册、海岸曲线、旧城档案感”。不要同时混入过多方向。

3. 提炼设计元素
   只抽取可用于界面的元素：
   - 线条：路线、海岸线、街区网格、山脊、河流、铁路。
   - 材质：纸张、瓷砖、混凝土、木、石、金属、老招牌。
   - 图形：局部纹样、票据边框、导视箭头、地图编号、邮戳。
   - 摄影/图片策略：真实地点、建筑、食物、海岸、市场、展览，不用泛旅游氛围图。

4. 定义 tokens
   至少定义 color、type、spacing、radius、shadow、component、map、motion。HTML 优先使用 CSS custom properties，不要到处写死样式值。

5. 应用到组件
   左侧控制台、日期卡、POI 卡、popup、marker、路线线条、资源抽屉、按钮、badge 和待重排状态都必须共享这套语言。
   只编辑单文件 `<style>` 中的颜色、字体、圆角、阴影、marker 和图层控件外观；不要为了视觉变化改列表、详情、地图和状态逻辑。

6. 审核一致性
   检查是否出现多个互相冲突的圆角、字号、阴影、按钮风格、marker 形状和警示色。

7. 审核用户语言
   检查地图可见文案是否使用旅行者能直接理解的表达，详见 `user-facing-language.md`。

8. 选择地图表达层级
   先判断目的地气质是否需要进入底图本身，再选择实现层级。不要让旅行者参与 renderer、WebGL 或 library 的技术选型。

## 必须定义的内容

`docs/design-language.md` 至少写：

- 视觉关键词。
- 参考来源：列出查过或使用的当地元素来源类型。
- 字号系统：title、section、card title、body、meta、button、popup。
- 色彩角色：background、surface、text、muted、accent、route、marker、warning。
- 组件语言：圆角、边框、阴影、按钮、badge、卡片密度。
- 地图元素：marker、路线线条、已安排点、候选点、必去但未安排点、待重排点。
- 图片和资源策略。
- 禁止事项。

## 设计元素使用规则

- 地图必须 map-first。底图、道路/地形/水域、POI 相对位置、marker、路线和筛选控件是主角；设计语言只能服务地图理解，不能把地图压成背景或插图。
- 在地元素优先进入整体色调、marker 样式、路线线、popup、侧栏、资源抽屉、badge、边框和状态表达。
- 在地元素要抽象使用，不要直接堆传统图案或国旗配色。
- 装饰元素必须服务信息层级，例如分隔、编号、状态、路线、抽屉背景。
- 左侧栏是工作台，优先清晰和密度；不要做成大字号旅游海报。
- 地图交互的状态色必须可读：已安排、候选、待重排、警示、已预约要能区分。
- 同一张地图中按钮、badge、卡片和 popup 的圆角、阴影、边框厚度应一致。
- 当视觉方向需要“随机感”时，marker 变体应从有限的形状与色彩 token 库中按 POI id 稳定分配；不要使用每次渲染都会变化的随机数，也不要让装饰色覆盖 event、selected、warning 等状态语义。
- 不规则 marker 必须在实际 24–28px 渲染尺寸下审核剪影；不要依赖贴着方形四角的 5–10% 微小切角，因为它们在底图上缩小后会重新读成正方形。使用更少、更深的切角，并以像素尺寸的浏览器截图验收。
- 当 marker 需要在选中态显示名称签、优先级或其他外置状态时，不要把 `clip-path` 放在整个交互容器上。使用不裁切的外层容器承载交互与标签，只让内层视觉 surface 接受轮廓裁切；否则外置信息会被一起裁掉。
- 目的地 preset 可以把已经存在的本地 raster 装饰资产复用为 selected marker 的表面纹理，但不得增加新的远程依赖，也不能用纹理替代 event、warning、pending reroute 等状态语义。
- 详情步骤、时间线圆点和地图 marker 是不同组件：正文中的顺序提示应保持轻量，不默认复用高识别度的地图 marker 轮廓。
- 只有实际支持拖拽的行才保留 drag handle 列；不可排序的候选项不应为隐藏手柄制造永久留白。

## 地图表达层级

- **基础地图**：Leaflet + raster tiles。适合大多数城市攻略，优先保证稳定、加载速度和离线文件可理解性。
- **目的地定制地图**：MapLibre + vector style 只有在用户明确要求改变地图表达和交互时使用，属于 interaction fork。当地貌、水域、道路、建筑、标签层级和路线表达需要共同塑造城市气质时才值得分叉。
- **空间叙事层**：Three.js 或 deck.gl 同样属于 interaction fork，只用于确实帮助理解的场景，例如山势、海拔、航线、潜点深度、潮汐、夜间城市段或大尺度跨城关系。它必须叠加在可操作的真实地图之上，不能替代 POI、缩放、筛选和路线编辑。
- 默认直接使用 Europe direct-copy interaction v1。只有用户明确提出、且当前路线和 marker 无法表达关键旅行信息时，才设计 vector 或 3D interaction fork；不要为了“高级感”分叉。
- 无论选择哪一层，都要保留同一份 POI、行程、优先级和调整状态，renderer 只负责表现，不另造一套旅行数据。
- renderer 只能把已经提供且复核的路径几何称为正式路线，不负责猜测道路。没有合格 geometry 时，显示编号地点；需要帮助扫读时可以增加标注为“顺序参考，不代表道路”的非交互虚线，但不能为它生成距离、移动时间或导航含义。用户调整后继续用状态表达“需要重新安排”。

## 常见设计方向示例

- 城市艺术/建筑：网格、博物馆导视、建筑线稿、展签感、克制中性色。
- 海岛/潜水：海况、船程、潮汐、潜点图层、低饱和蓝绿，不做廉价度假海报。
- 南洋旧城：骑楼、招牌、票据、会馆、旧报纸、咖啡店材质，避免过度怀旧滤镜。
- 酒庄/自驾：路线编号、预约窗口、山谷等高线、纸质手册、驾驶风险提示。
- 巴西城市/海岸：现代主义建筑线条、海岸曲线、Bahia 色彩和街区材质；避免直接使用高饱和国旗绿黄铺满界面。

## 禁止事项

- 只改主色，不定义字号和组件规则。
- 每个组件各自写一套颜色、圆角和阴影。
- 使用和目的地无关的通用渐变、装饰圆点或 stock 风背景。
- 把当地文化元素当贴纸堆在界面上。
- 把地图做成海报、手账、画册或装饰插画，导致底图、道路、POI 相对位置和 marker 不清楚。
- 为了视觉牺牲筛选、popup、路线编号、移动端可读性。
- 用 Three.js 手绘一张不能正常缩放、筛选、定位和修改行程的假地图。
