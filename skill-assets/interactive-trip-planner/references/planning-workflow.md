# 规划流程和每日路线标准

## 目录

- 启动说明
- 最小启动信息
- 一次旅行设计提案
- 深度规划
- 地图修改后的重排
- 每日路线标准

## 启动说明

开始完整攻略前，用 2-3 句话向用户说明：先理解关键需求，再给一次旅行设计提案；用户确认后，才制作攻略文档、地点资料和动态地图。

示例：

```text
我会先确认会影响路线的关键信息，再给你一版旅行设计提案，讲清楚这趟旅行的主线、经过哪些地方、酒店和吃饭如何服务动线。你确认方向后，我再复核资料并制作可以继续调整的旅行地图。
```

不要一开始进入酒店清单、景点清单或地图实现。

## 最小启动信息

第一轮最多询问 3-5 组问题。每组可以合并相关信息，不逐项发送问卷。

优先确认：

1. 日期、目的地、出发地、抵达和离开方式。
2. 同行人、体力、作息和希望的旅行节奏。
3. 必去、不想去和明显兴趣。
4. 会改变路线的交通方式，例如自驾、公共交通或包车。
5. 预算敏感度、已定住宿或强住宿要求。

用户已经给出的信息不要重复问。信息足够时直接整理理解，不为了填满字段继续提问。

### 必须立即澄清

只在缺失信息会改变路线结构、预算、安全或可执行性时立即提问，例如：

- 日期、抵达和返程条件彼此冲突。
- 同行人有老人、小孩、行动限制或明显体力边界。
- 自驾、包车和公共交通会产生完全不同的城市组合。
- 预算差异会改变酒店区域或主要体验。
- 签证、跨境或航班条件会决定能否进入某地。
- 用户明确要求高风险或强天气依赖活动。

### 按条件后置

- 海岛或潜水路线出现后，再问游泳能力、证照、浮潜/体验潜/水肺偏好、晕船和飞行缓冲。
- 自驾路线出现后，再问驾照、驾驶经验、停车和异地还车。
- 酒吧和深夜路线出现后，再问夜间安全和回程边界。
- 进入酒店筛选后，再问床型、电梯、停车、安静、景观和取消政策。
- 吃喝成为主线后，再问饮食禁忌、正式餐预算和排队接受度。

单个咖啡、甜品、同街区餐厅和普通备选地点可以暂定，并明确后续可替换。

## 一次旅行设计提案

提案把主题、路线思路、酒店和吃饭逻辑、同期活动与地图气质合并交付。用户只需要确认一次主方向。

### Visitor mode 与游客/在地平衡

先根据用户的到访历史和明确偏好选择一个 visitor mode：`first-visit`、`return-visit`、`landmark-light`、`local-only` 或 `balanced-visitor`。第一次使用当前 Skill、第一次咨询或第一次规划不等于第一次到访目的地；用户没有说明到访历史时，必须写“到访史未知”，只能暂定 `balanced-visitor`，不得声称首次到访。“想更 local”、喜欢市场或社区酒吧，不能自行推断为 `local-only`。

每座有至少两个完整旅行日的城市都先至少评估 3 个代表性景点，并逐项写明采用或舍弃理由：它们是否帮助理解目的地、与主线和日期是否匹配、预约与绕路成本是否合理。`first-visit` 或到访史未知的 `balanced-visitor` 通常在该城市停留段内保留 2–4 个代表性主锚点，而不是把游客理解和当地生活做成二选一。每个保留的代表性主锚点都要连接同方向当地生活角色：市场、居民广场、社区空间、街区咖啡、社区饭馆、传统商业或短半径夜间体验，让主锚点成为进入当地生活的一段动线，而不是孤立打卡。

`return-visit`、`landmark-light`、`local-only`、预约失败或过度绕路可以减少或不采用这些锚点，但必须在提案和正式路线中写明适用的 visitor mode 与具体理由。重型景点每天最多 1 个；其余主锚点、用餐与休息仍按 1-3 个日主锚点和真实动线安排。

### 主题判断

用户偏好明确时，直接归纳一个暂定主线，不强制再列 3-5 个候选。例如用户已经提出“里斯本旧城生活 + 亚速尔观鲸”，可以整理为“山城日常 + 大西洋回声”双主题并请其确认。

用户只给日期和目的地、没有明显体验倾向时，再给 3-5 个主题候选。每个候选写清：

- 主题名和经过地点。
- 2-5 个行程段及其名字。
- 每段看什么、吃什么、为什么值得。
- 强化什么、牺牲什么、适合什么节奏。

主题必须能指导城市取舍、酒店区域、每日路线和地点优先级，不能只是营销口号。

### 提案结构

```text
我理解的旅行需求：
用 2-4 句话复述日期、同行人、节奏、兴趣和硬约束。

暂定旅行主线 / 主题候选：
说明这趟旅行在体验什么，以及为什么适合用户。

行程段：
- 《段落名》：经过哪里，看什么、吃什么、为什么值得。
- 《段落名》：经过哪里，看什么、吃什么、为什么值得。

同期活动和在地元素：
哪些节庆、展览、市集、演出、自然体验进入路线，哪些只做备选或避让因素。

我会怎么取舍：
保留什么、降低什么、暂时不安排什么，并说明原因。

酒店和住宿：
适合住在哪些区域，如何影响出发、回程、午休、夜间安全和跨城交通。

吃饭和休息：
正式餐、地方经典、小吃、咖啡、甜品、酒吧前轻餐和保底餐如何服务路线。

每日路线骨架：
每天 1-3 个主锚点和顺路备选，说明为什么这样排。

游客与在地平衡：
写明 visitor mode 和到访史；每座两天以上城市至少 3 个已评估代表性景点的采用或舍弃理由；以及每个保留代表性主锚点同方向连接的当地生活角色（市场、居民广场、社区空间、街区咖啡、社区饭馆、传统商业或短半径夜间体验）。

地图气质：
用自然语言说明视觉感受和当地元素，不要求用户理解实现方式。

还需要确认：
只列会显著改变路线的 2-5 项。
```

用户确认后开始深度复核和落文件。用户明确要求跳过提案、只做局部修改、或当前对话已经确认主线时，可以直接执行。

## 深度规划

1. 复核交通、开放时间、闭馆日、预约难度、同期活动、天气、安全和价格。
2. 扫描当地节庆、展览、演出、市集、体育赛事、公共假日、宗教活动和季节性自然体验，并按 `references/event-schema.md` 写入或复核 `data/events.json`。
3. 对每项活动审查其路线影响：封路或闭馆、拥挤、晚间结束时间、订票/预约和交通变化；即使旅行者不参加，也要把避让、缓冲或改乘判断写入当天语境。
4. 设计城市或区域段，控制跨城成本和移动日强度。
5. 把酒店作为每天的出发、回程、休息和夜间安全锚点。
6. 每天安排 1-3 个主锚点；`first-visit` 或到访史未知的 `balanced-visitor` 的城市有至少两个完整旅行日时，逐城至少评估 3 个代表性景点并写明采用或舍弃理由，通常在该城市停留段内安排 2–4 个代表性主锚点，且重型景点每天最多 1 个。每个代表性主锚点要接入同方向当地生活角色：市场、居民广场、社区空间、街区咖啡、社区饭馆、传统商业或短半径夜间体验；其余地点围绕自然动线、交通轴线、驾驶顺序或时间窗口补充。
7. 餐厅、酒吧、咖啡和甜品按当天区域、体力和预约时间安排，不作为填空。
8. 建立比正式路线更丰富的备选地点，用于天气、预约、排队和体力变化。
9. 先生成并验收 Core 地图：全程总览、某一天、地点详情、修改、撤销、重新安排和状态恢复。
10. Core 通过浏览器验收后，再按目的地需要增加图片、专题信息和视觉设计。用户未要求视觉深化时，不阻塞交付。

提案中的“地图气质”只描述旅行者会感受到的视觉方向，不要求用户审批地图技术，也不应在此阶段启动高级地图或动画实验。

## 地图修改后的重排

地图中的优先级和日期修改先作为用户选择保存，不直接宣称正式路线已经合理。

地图向用户显示：

- 改了几个地点。
- 哪些地点加入、移出或改了优先级。
- 哪几天需要重新安排。
- 哪一天可能过满、折返或跨区。
- “请 Codex 重新安排”操作。

普通修改直接保存并提供“撤销上一步”：调整普通地点优先级、把同城普通候选加入未满日期、调整同日顺序。住宿、已预约、固定时间、当前必去、跨城市或超容量等高影响修改，先展示规划级影响，用户确认后才保存。

“请 Codex 重新安排”生成可复制的自然语言请求，例如：

```text
你调整了 3 个地点：把罗丹美术馆加入 4 月 8 日，把圣日耳曼晚餐改成“优先去”，并从 4 月 9 日移除了杜乐丽花园。4 月 8 日新增地点后可能偏满，建议重新检查午后路线。
```

请求必须包含旅行名称、全部修改、原日期、新日期、优先级变化和受影响日期，不依赖 Codex 读取浏览器保存状态。静态 HTML 只负责展示和复制，不声称能直接向当前 Codex 对话发送消息。

内部可以记录地点编号、原日期、新日期和优先级变化，但不要要求用户阅读或编辑这些数据。Codex 收到请求后，重新检查营业时间、交通、用餐、体力、酒店基地和同日容量，再更新正式路线。

## 每日路线标准

- 每天 1-3 个主锚点，避免全天塞满“必须去”。
- `first-visit` 或到访史未知的 `balanced-visitor` 的两天以上城市，每座至少评估 3 个代表性景点并写明采用或舍弃理由，通常在该城市停留段内保留 2–4 个代表性主锚点；重型景点每天最多 1 个。每个保留锚点同方向连接当地生活角色：市场、居民广场、社区空间、街区咖啡、社区饭馆、传统商业或短半径夜间体验，形成游客理解和当地生活连续的一段路线。
- 只有明确 `return-visit`、`landmark-light`、`local-only`、预约失败或过度绕路时，才能偏离上述数量；当天说明必须写出原因。
- 备选地点不必都在同一街区，但应顺着当天交通和步行方向，少折返，不为普通地点横穿城市。
- 移动日只安排抵达后顺路、低强度、可取消的活动。
- 晚间路线控制安全半径，不做深夜长距离步行换场。
- 自驾路线按驾驶顺序、停车和回程风险组织。
- 公共交通城市按线路、换乘成本和步行区域组织。
- 海岛、徒步、自然和酒庄路线按天气、体力、预约和返程风险组织。
- 远距离地点必须说明价值、交通、时间成本、风险和近处替代。

### 日内动线验收

“都在旧城”或“看起来距离不远”不等于路线顺。每一天在写入地图前必须完成一次日内动线验收：

1. 先列固定时间窗：预约、演出、开门、最后入场、餐厅订位、交通班次。
2. 再列完整时间线：酒店出发、每个正式地点、午餐和休息、必要的回酒店、晚餐和回程。不能把回酒店或取行李藏在两个地点之间。
3. 对每两个相邻地点记录交通方式、规划时间和复核依据。正式路线中不得出现跳过中间地点的移动说明。
4. 有 4 个以上正式停靠点时，使用 walking、driving 或 transit 路网比较至少两种满足时间窗的顺序。先排除迟到、闭馆和过度疲劳，再比较总移动、折返和换乘。
5. 酒店休息、固定预约、安全回程或景观时段造成的折返可以保留，但必须在当天说明中写清“为什么值得折返”。普通候选不能造成折返。
6. 午餐、咖啡和甜品优先放在主轴上承担休息，不为一顿可替换的餐横穿街区。
7. 保存复核后的顺序判断、固定约束和有意折返。地图有真实路网几何时才绘制正式路线；没有时只显示顺序和“这段尚未复核”。

向旅行者解释时使用自然语言，例如：“上午从酒店向东进入娘惹宅邸，之后沿多元宗教街区一路向西南；午餐后到旧城南端，再向北走到 15:30 的蓝屋导览。导览后唯一一次折返是回酒店休息，再去晚餐。”不要展示算法名、字段名或内部评分。

交付前检查：

- 每一对相邻地点都有移动说明。
- 地图上的正式路线经过所有正式停靠点，没有穿楼、跨水或用坐标直线代替道路。
- 地点顺序满足固定时间窗，午餐和休息有真实位置。
- 有意折返已经解释；无法解释的折返已经移除或降为候选。
- 用户调整地点后，旧路线只标记为需要重新安排，不自动生成新路线。

输出区分：

- 正式路线：建议当天执行。
- 当天备选：可以替换或顺路加入。
- 其他地点：保留资料，不建议专程前往。
