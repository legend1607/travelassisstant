## 选择地区来源包

0.1.0 开始，完整规划先读取 references/regional-source-packs.md，并从 assets/source-packs/index.json 选择 Global Base 与一个匹配的地区包。Global、中国大陆、日本、法语区（法国与比利时）是首发 required subset；registry 可以加入通过通用 validator 的新地区包。其他尚无有效 pack 的目的地使用 Global Base、目的地官方入口与三语动态搜索，不能把尚未维护的地区写成已覆盖。

每条来源先按 A/B/C 可访问性探测，再进入搜索漏斗。B/C 级入口不是默认自动成功；失败时执行记录内的 fallback。编辑发现必须使用具名本地编辑源，并声明 city-life-culture、food-drink、events-listing、local-news 或 industry-specialist subtype，不保存模糊的“当地媒体”记录。

十类查询意图、三语 query、来源字段、搜索漏斗和中国大陆 amap-gui 降级见 references/regional-source-packs.md。能力探测不能替代实际搜索，地图坐标也不能替代真实路线。

### 安全来源访问探测

当需要先判断某个已选来源当前是否可访问时，可把**明确请求的**来源交给 `node skill/scripts/probe-source-access.js --context <sources.json>`，或使用 `--stdin`。输入是 `{ "sources": [{ "id": "...", "url": "...", "fallback": "..." }], "timeoutMs": ..., "concurrency": ... }`，也可直接传入已验证的 pack source（其 fallback 在 `source.access.fallback` 字符串数组中）；只允许无内嵌用户名或密码的 `http`/`https` URL，`concurrency` 最大为 4。请求保留原 URL 的 query/fragment，输出才会移除它们，避免展示脱敏改变实际访问的资源。

Probe 先以不跟随跳转的 HEAD 检查；只有 405/501 才以 `Range: bytes=0-1023` 的 GET 降级，且不会读取响应正文。结果只描述 `reachable`、`redirected`、`rate-limited`、`access-blocked`、`server-error`、`not-found` 或 `network-error` 等访问状态，并给出 `httpStatus`（网络失败为 `null`）；401/407 与其他非 404/429 的 4xx 归为 `access-blocked`，只有 5xx 归为 `server-error`。不输出 headers、cookie、authorization、正文、凭据或原始 query。顶层 URL fallback 仅输出安全化 URL；`source.access.fallback` 只输出 availability 与 option count，不回显原文。Probe 不会自动访问任何 fallback；主访问为 `reachable` 时标记 `available`，其他状态标记 `fallback-required`。

这是 access-only 信号，不能证明 POI、场馆或餐厅真实存在、仍在营业、可订、适合用户、路线可行或安全。访问成功后仍必须回到官网、经营方、主办方、票务或交通方复核具体事实；失败也不等于来源内容错误。

## 搜索前建立任务单

开始搜索前先写一份内部搜索任务单，不需要让用户填写问卷。至少包含：

| 项目 | 要记录的内容 |
| --- | --- |
| 时间 | 旅行日期、星期、季节、公共假日、抵达和离开时间 |
| 空间 | 国家、城市、街区、周边地区和跨城关系 |
| 用户 | 同行人、体力、兴趣、饮食、安全、预算和交通偏好 |
| visitor mode | `first-visit`、`return-visit`、`landmark-light`、`local-only` 或 `balanced-visitor`；第一次使用 Skill、第一次咨询或第一次规划不能代替到访历史，未知时记录“到访史未知”和 `balanced-visitor` |
| 旅行主线 | 已确认的主题、行程段和明确取舍 |
| 地点角色 | 主锚点、当地生活、酒店、用餐、夜间、交通、休息和替代方案 |
| 易变化事实 | 营业、闭馆、活动、票务、价格、时刻、天气、海况、签证和安全 |
| 搜索语言 | 中文、英文和目的地当地语言；记录地点正式名称与常见别名 |

先列“这次搜索要回答的问题”，例如：

- 巴塞罗那三天中，哪一天适合高迪建筑，哪一天适合旧城和夜间酒吧？
- 10 月底是否有会改变路线的节庆、展览或公共假日？
- 酒店住在哪个交通节点能同时服务白天步行和夜间回程？
- 某个潜点是否适合用户证照、季节和离境航班时间？

没有明确问题时，搜索容易退化成复制“十大景点”。

## 六层搜索顺序

### 第一层：建立目的地事实骨架

先确认城市关系、季节、交通结构、公共假日和主要区域，不急着选具体餐厅。

优先来源：国家或城市旅游局、城市文化日历、交通运营方、机场和车站、国家公园或文化机构。

要回答：

- 旅行日期落在哪个季节、星期和公共假日？
- 城市之间真实移动成本是多少？
- 哪些街区适合步行，哪些地点需要单独交通？
- 是否存在闭馆规律、施工、罢工、宗教时段或季节风险？

### 第二层：按主题和地点角色发现候选

围绕用户主题搜索，而不是只搜“best things to do”。每个行程段分别搜索：

- 核心体验：建筑、艺术、历史、自然、潜水、酒庄、夜生活等。
- 当地生活：市场、社区空间、街区商业、公共空间、传统行业和本地活动。
- 吃喝角色：地方经典、正式餐、小吃、咖啡、甜品、酒吧前轻餐和保底餐。
- 住宿基地：服务每日动线、晚间回程、行李和跨城交通的区域与酒店。
- 风险替代：下雨、闭馆、预约失败、晕船、体力不足时可替换的地点。

这一层可以使用官方专题、当地文化媒体、专业榜单、地图平台和近期社区内容发现名称，但只把它们当作候选线索。

每座有至少两个完整旅行日的城市先至少评估 3 个代表性景点，并记录每项采用或舍弃理由；`first-visit` 或到访史未知的 `balanced-visitor` 通常在该城市停留段内保留 2–4 个代表性主锚点，并为每个锚点检索同方向当地生活角色：市场、居民广场、社区空间、街区咖啡、社区饭馆、传统商业或短半径夜间体验。著名景点不能只因为游客多就被排除；只有明确 `return-visit`、`landmark-light`、`local-only`、预约失败或过度绕路时才可不采用，并记录理由。

### 第三层：扫描同期活动和在地元素

完整攻略必须按旅行日期搜索：

- 节庆、宗教仪式、城市纪念日和公共假日。
- 展览、演出、音乐节、电影节、艺术节和体育赛事。
- 市集、夜市、跳蚤市场、农夫市场和街区活动。
- 游行、会议展会、交通管制和大规模活动。
- 花期、雨季、极光、海况、迁徙、采收季和国家公园季节规则。

先查主办方、场地方和城市官方日历。活动聚合页只用于发现，不能作为活动日期和票务的最终依据。

### 第四层：逐个核实准备采用的地点

对可能进入正式路线或重要备选的地点，使用准确名称逐项检查：

- 官方名称、地址、入口和地图位置。
- 旅行日期当天是否开放，是否有季节性或星期闭馆。
- 预约入口、放票窗口、入场规则和取消政策。
- 价格、菜单、最低消费、年龄和着装要求。
- 建议停留时间、排队、无障碍、行李和摄影限制。
- 为什么适合当前用户，以及和当天其他地点如何衔接。

搜索摘要只能帮助定位网页，不能作为事实来源。必须打开支持结论的具体页面。

### 第五层：检查路线可执行性

地点本身值得去，不等于能放进这一天。继续检查：

- 官方交通线路、班次、首末班、换乘和步行入口。
- 酒店到早晨第一站、晚餐或酒吧后的回程。
- 自驾停车、限行、收费、取还车和酒后驾驶风险。
- 轮渡、潜水船、缆车、山区道路和天气取消规则。
- 正式餐预约时间与前后景点的距离和缓冲。

路线几何优先使用可靠路网结果或人工复核，不用地点坐标直线推测真实路径。

### 第六层：用体验来源补充现场感

地图评价、小红书、抖音、Instagram、Reddit、旅行论坛和近期媒体用于补充：

- 实际排队、热门时段和预约体验。
- 点单建议、份量、座位、噪音和服务节奏。
- 拍照视角、入口难找、中文游客常见误区。
- 夜间街区感受、打车难度和近期施工线索。

这些内容是体验线索，不单独证明营业时间、票务、法规、安全结论或活动是否存在。出现重要线索后回到官方或运营方复核。

## 查询词怎么写

### 使用三种语言

不要只用中文。至少组合：

1. 中文：理解中文旅行者常见问题和体验。
2. 英文：寻找官方国际页面、专业媒体和通用资料。
3. 当地语言：寻找城市日历、当地媒体、菜单、交通公告和正式名称。

先确认地点的正式名称、当地拼写和常见英文名，再继续深搜，避免同名地点或错误城市。

### 查询模板

用具体地点、日期、事实和来源类型组成查询词：

```text
[城市当地名称] official tourism [旅行月份 年份]
[城市当地名称] agenda cultural [当地语言月份 年份]
[城市] [具体日期] festival exhibition concert official
[地点正式名称] official opening hours tickets
[地点正式名称] closed [星期或旅行日期]
[餐厅正式名称] official menu reservation
[酒吧正式名称] official menu booking dress code
[起点] to [终点] official train bus ferry
[国家公园/潜点] official conditions permit weather season
site:[官方域名] [活动或地点关键词]
```

示例：

```text
site:barcelona.cat agenda octubre 2026
Barcelona 24 October 2026 festival official
Sagrada Familia official tickets opening hours October 2026
Musée d'Orsay official Thursday opening hours tickets
Chew Jetty Penang official heritage opening access
Semporna diving October visibility official marine weather
```

搜索未来活动时同时搜索“月份 + 年份”和“具体日期”；如果节目尚未发布，查上一届发布时间，用于判断何时重新复核，但不能把上一届安排写成本届事实。

### 活动从发现线索到当前活动

把发现与推广分开记录在 `data/events.json`。历史届次不是当前活动：过去节目、旧届页面和二手推荐只能保留为 `historical-lead`，用于发现名称、主办方和通常发布时间，不能展示为旅行日期的活动。只有主办方、场地方、城市日历或官方票务支持当期窗口时，才可升为 `announced` 或 `program-pending`；前者已有可考虑的官方日期窗口，后者只有官方窗口、节目尚待发布。官方同时确认具体场次、时间和场地后才升为 `confirmed`。每次推广都记录当期官方 URL、`sourceIds` 和需要再次检查的时间；范围、状态和路线引用遵循 `references/event-schema.md`。

### 分批查询

先用 3-4 组不同意图的查询建立候选，再对短名单逐项深搜。不要连续改写同一句“best places”，也不要一次打开大量同质榜单。

建议查询意图：

- 官方事实查询。
- 主题和在地文化发现。
- 同期活动查询。
- 路线和交通查询。
- 近期体验与风险查询。

## 候选数量基线

数量是质量下限，不是凑数任务。候选池以正式路线预计使用量的 2-3 倍为默认目标，才能真正支持用户探索、整条路线替换和后续重新安排；但每个地点仍然必须有明确角色。

### 按完整旅行日计算

每个完整旅行日准备约 12-18 个可地图化地点。一天实际可能使用 4-6 个地点，其中只有 1-3 个主锚点；其余候选用于形成第二套路线、同方向替换、吃饭休息和用户自由探索。这里的数量包含景点、活动、餐饮、咖啡甜品、夜间体验、休息点和替代方案，不包含酒店本身与仅用于换乘的交通节点。

| 在同一城市或区域的停留 | 地点候选基线 | 适用说明 |
| --- | --- | --- |
| 抵达、离开或纯移动日 | 6-10 个 | 酒店附近轻食、散步、补给、夜间和天气替代，不按完整日灌满 |
| 1 天停留 | 12-18 个 | 一条正式路线、一条可整体替换的路线，以及少量扩展候选 |
| 2-3 天停留 | 24-45 个 | 覆盖不同主题日、街区、用餐角色和天气变化 |
| 4-5 天停留 | 40-70 个 | 形成多个路线簇和专题候选，不要求每天使用全部地点 |
| 6 天及以上 | 55-90 个 | 先覆盖主要主题，再按用户兴趣扩展；避免同类地点无限累积 |

超大城市、多主题旅行或用户明确希望丰富浏览时，可以在区间上限基础上增加约 20%-30%。小岛、单一活动区、短暂停留或资料确实有限的地方可以低于基线，但必须说明原因，并确认正式路线、完整备选路线、吃饭和风险替代仍然成立。

### 三层候选结构

每个完整日尽量形成三层，而不是一份没有层级的长清单：

1. 正式路线：预计真正使用的 4-6 个地点，包括 1-3 个主锚点以及必要的用餐、休息或夜间地点。
2. 可直接替换：约 4-6 个已经确认位置和关键限制的候选，能够组成第二套顺路路线，或替换正式路线中的同类地点。
3. 扩展候选：约 4-6 个有独特价值的地点，适合用户继续筛选、临时加入或留到下一版重排。

不同层可以根据主题调整，但正式路线之外必须至少有一套真正可执行的替代组合，不能只准备零散单点。

## 分类覆盖基线

候选数量和分类覆盖必须同时满足。标准城市完整日以 12-18 个不重复地点为基础，至少覆盖以下角色：

| 分类或体验角色 | 每个完整日的建议基线 | 说明 |
| --- | --- | --- |
| 景点、博物馆或核心体验 | 4-6 个 | 包含 1-3 个正式主锚点，以及同主题或低体力替代 |
| 当地生活、街区或市场 | 2-4 个 | 市场、社区空间、传统商业、公共空间或本地活动 |
| 正餐候选 | 4-6 家 | 午餐和晚餐分别保留首选与保底；正式路线通常只选 1-2 家 |
| 小吃、咖啡、甜品或休息 | 3-5 家 | 服务步行休息、补给、下午时段和临时替换 |
| 夜间体验 | 0-6 家 | 没有夜生活需求可以为 0；计划喝酒时按路线组合增加 |
| 购物、设计或手作 | 0-3 个 | 只有用户感兴趣或目的地具有独特价值时加入 |
| 雨天、闭馆或低体力替代 | 2-3 个 | 可以与博物馆、市场、咖啡或其他室内地点重叠 |

分类数字不能简单相加，因为同一个地点可以承担多个角色：市场既是当地生活，也可能是小吃和午餐；一间设计书店可以同时属于购物、休息和街区体验。统计唯一地点总数时只计一次，同时在地点资料中标出它承担的全部角色。

### 按主题调整

基础盘不是所有目的地使用同一个分类比例。根据已确认主题调整：

- 城市艺术、建筑或历史：核心体验提高到 6-8 个；餐饮和休息仍需保留，不得只做景点清单。
- 吃喝主线：正餐提高到 6-10 家，小吃、咖啡和甜品提高到 5-8 家；核心景点可以降到 3-5 个，但仍需保留城市语境。
- 酒吧或夜生活主线：每个计划夜晚准备 4-6 家短半径候选；如果是核心主题可提高到 6-10 家，并按晚餐、第一杯、第二站和安全回程组织。
- 海岛、潜水或自然：自然和活动候选 4-6 个，天气或取消替代 3-5 个，餐饮 3-5 家；同时补交通、资质、海况和飞行缓冲资料。
- 自驾或酒庄：目的地、酒庄或沿途体验 4-6 个，正餐与补给 3-5 家，停车、驾驶顺序和返程风险必须覆盖。
- 亲子或低强度：核心体验 3-5 个，餐饮 3-5 家，室内休息、厕所、低体力和可取消候选 3-5 个。

多日停留按当天路线区域检查分类，不只看整座城市总数。例如城市共有 20 家餐厅，但某一天的主路线附近没有现实可用的午餐，仍然属于覆盖不足。

### 必须覆盖的地点角色

数量达标仍不代表搜索完整。至少检查：

- 每个完整旅行日有 1-3 个正式路线主锚点。
- 每天至少有一套由 3-6 个地点组成的同方向、同角色或更低体力替代路线。
- 每个需要外出就餐的主要时段至少有一个首选和一个现实可用的保底选择；同一家店可以服务多个角色，但不能假装已经订到。
- 每 1-2 个完整旅行日至少有一个市场、社区空间、街区生活或其他在地生活候选，除非目的地类型不适用。
- 每个天气、闭馆或预约依赖较强的主锚点至少有一个替代方案。
- 用户尚未确定住宿时，每个住宿基地比较 2-5 个酒店或明确不同住宿区域，不把酒店数量混进地点候选基线。
- 一晚计划去 2 家酒吧时，酒吧候选至少准备 4-6 家，并优先组成两套各 2-3 家、步行或短程打车可连接的路线；夜生活是主线时可以扩大到 6-10 家，但仍要按街区和回程方向分组。
- 潜水、酒庄、徒步、亲子等成为主题时，额外覆盖该主题的安全、交通、资质、预约和保底角色，不能只增加同类热门点。

地点可以同时承担多个角色，例如市场既是当地生活也是午餐候选。不要为了让每一类数字单独达标而重复或增加低质量地点。

### 分层复核

数量提高后，不要求所有候选使用同样深度复核：

- 正式路线：完整检查官网、日期、营业或场次、预约、交通、停留时间和主要风险。
- 可直接替换：至少确认地点仍存在、旅行日期可用、位置合理、关键预约和关闭风险；被选入正式路线后补齐完整复核。
- 扩展候选：确认名称、位置、体验价值和可靠发现来源，可以标记“需要临近复核”。
- 只有榜单或社区帖子线索、尚未确认位置或营业状态的地点标为“待复核”或 `lead-only`，不计入 12-18 个可用候选基线。

## 候选地点漏斗

### 发现

广泛收集可能服务主题的地点，保留来源和发现理由。此时不急着给“必去”。

### 初筛

按以下维度判断：

- 用户兴趣和同行人是否匹配。
- 是否能表达目的地独特性，而不是在其他城市也能替代。
- 是否服务已确认的旅行主线和行程段。
- 是否顺着酒店、交通和当天路线。
- 时间、预算、预约和体力成本是否合理。
- 资料是否足够可信，风险是否可管理。

平台评分和榜单名次只能帮助发现，不能替代上述判断。

### 深度复核

只有进入正式路线、酒店对比、正式餐或重要备选的地点才需要完整复核。普通顺路候选可以记录资料线索和“需要临近复核”，避免把时间耗在低影响细节上。

### 安排行程角色

为保留地点写清：

- 为什么适合用户。
- 在旅行主线中承担什么角色。
- 适合哪一天和哪个时段。
- 与哪些地点顺路或可以互相替换。
- 预约、营业、天气、安全和预算注意事项。

对著名但未采用的地点说明具体取舍，例如跨区成本过高、主题重复、闭馆、预约冲突或不符合体力，而不是简单说“不推荐”。

## 事实复核和冲突处理

以下信息必须使用当前来源：

- 营业时间、闭馆日、临时关闭。
- 活动日期、演出场次、票务和预约。
- 交通时刻、线路、施工、罢工和末班车。
- 价格、套餐、最低消费和取消政策。
- 签证、入境、当地法规和安全提示。
- 天气灾害、季风、海况、能见度和自然保护区规则。
- 餐厅或酒吧开业、停业和榜单年份。

复核规则：

1. 易变化且高影响的事实，尽量使用至少两个相互独立的来源，其中一个应为官方、主办方、场地方或运营方。
2. 官方来源缺失时，不把推断写成事实；标为“需要复核”，并说明当前依据。
3. 搜索摘要、AI 摘要和地图自动标签不是最终证据，必须打开原页面。
4. 引用支持具体结论的页面，不只记录网站首页。
5. 记录实际检查日期。旅行临近时，对营业、票务、交通、天气和安全重新检查。
6. 多个来源冲突时，写清冲突内容、采用哪个来源和原因；不能静默挑选更方便的答案。
7. 过去一届活动、旧菜单、旧票价只能帮助判断搜索方向，不能直接当作旅行日期的事实；历史届次不等于当前活动。

## 资料记录格式

### 正式路线的证据边界

来源 `role` 要明确区分事实（`fact`）、推荐/发现（`recommendation` 或 `discovery`）和体验（`experience`）：事实来源支持地址、开放、菜单、场次等可核实结论；推荐来源支持“为什么进入候选”和值得点的品类，但不能自动证明营业或库存；体验来源补充排队、服务节奏、入口和现场感，不能单独支持法规、安全或当前活动。

每条正式路线地点在内部数据中保存非空 `sourceIds`。被引用的来源必须包含非空 `id`、`title`、`type`、`role`、`language`、`checkedAt`、`status`、非空 `supports`，以及安全公开 URL：只允许 `http:` / `https:`、非空 hostname 与空 username/password。构建器以 `new URL(...).href` 规范化后才公开序列化；活动 `officialUrl` 使用同一边界。`supports` 只列这张页面真实支持的结论；来源角色不同不代表可信度高低，而是限制它能证明什么。

生成公开地图时，构建器按 `sourceIds` 顺序解析并只输出 `{title,url,type,role,language,supports,checkedAt,status}` 八字段 `evidenceSources`；公开数据不得保留 raw `sourceIds`。地图把这些资料放在可展开的“资料依据”中，而不是给每个地点增加常驻置信度徽章。

`validate-trip-data.js --sources <sources.json>` 会检查来源注册表的 id、必填字段、`supports` 和 HTTP(S) URL，但不会自动把路线升级为正式证据合同；只有同时使用 `--require-route-evidence`，才会检查 canonical `routeStops` 和公开母版的正序 `defaultAssignments`。新攻略最终运行：

```bash
node scripts/validate-trip-data.js --pois <pois.json> --itinerary <itinerary.json> --sources <sources.json> --require-route-evidence --strict-routes
```

不带 `--require-route-evidence` 的 legacy 成功只表示旧数据仍兼容，不是正式路线的证据认证。

在 `data/sources.json` 保存结构化来源：

```json
{
  "id": "source-sagrada-official-hours",
  "title": "Sagrada Familia official opening hours",
  "url": "https://...",
  "type": "official",
  "role": "fact",
  "language": "es",
  "checkedAt": "2026-07-18",
  "supports": ["opening-hours", "tickets", "entry-rules"],
  "recheckBefore": "2026-10-15",
  "status": "confirmed",
  "notes": "10 月具体入场时段仍以购票页为准"
}
```

`status` 建议使用：

- `confirmed`：当前来源已经支持结论。
- `recheck`：当前可用于规划，但出发前需要再次核实。
- `lead-only`：只是发现线索，不能支持正式事实。
- `conflict`：来源冲突，尚未解决。

在 `docs/sources.md` 用自然语言记录：

- 哪些事实已经确认。
- 哪些事项需要在什么时间再次检查。
- 哪些来源存在冲突。
- 哪些著名地点被排除，以及路线取舍理由。

地点数据中的 `source` 应引用来源编号。一个来源只标记它实际支持的事实，不能让餐厅榜单来源同时“证明”营业时间、价格和夜间安全。

不需要保存全部搜索历史，但要保存最终采用和影响判断的来源。不要记录搜索结果摘要作为来源。

## 停止搜索的条件

同时满足以下条件时停止继续扩展，转入排程：

- 地点数量达到与完整旅行日相匹配的基线；低于基线时已经写明目的地限制和不继续凑数的理由。
- 每个行程段已有能表达主题的核心地点。
- 每天预计有 1-3 个主锚点，并有同方向、同角色或天气适配的替代方案。
- 酒店基地、主要用餐角色、跨城交通和晚间回程已经有可执行方案。
- 正式路线候选的高影响事实已经确认，或明确标记重新复核时间。
- 必去与著名落选地点都有可解释的选择理由。
- 新一轮搜索结果主要重复已有候选，没有带来新的主题价值或更好的路线方案。
- 不存在尚未澄清且会改变城市组合、安全或可执行性的重大问题。

不要因为找到第一个热门清单而停止，也不要为了“资料更全”无限增加地点。候选池应比正式路线丰富，但每个地点都必须有角色。

## 给用户的表达

不要向用户倾倒查询词、来源层级和内部评分。用自然语言交付：

- 为什么选择这些地点，它们如何服务旅行主线。
- 哪些地点是正式安排、当天备选或留档。
- 为什么没有选择其他著名地点。
- 哪些营业、活动、票务或交通已经确认。
- 哪些信息需要临近出发再次检查。

重要结论区分：

- 事实：当前官方来源、场地方、运营方或已验证资料直接支持。
- 推断：根据位置、时间、体力和体验关系做出的判断。
- 建议：最终路线取舍和替代方案。

## 常见错误

- 只搜索中文攻略或“十大景点”。
- 只按地图评分、平台热度或榜单名次排序。
- 用搜索结果摘要、AI 摘要或旧攻略确认营业和票务。
- 找到地点但不解释为什么适合这个用户。
- 搜索很多景点，却没有酒店、吃饭、休息、交通和替代方案。
- 为了塞入低优先级地点制造折返和跨区移动。
- 把社区体验写成官方事实，或忽略社区发现的近期风险线索。
- 没有记录检查日期和重新复核时间。
- 资料还不稳却在地图中显示为已确认。
