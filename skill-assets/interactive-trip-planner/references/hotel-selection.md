# 酒店选择和解释标准

酒店不是住宿列表，也不是最终给一个名字就结束。酒店会决定每日出发、回程、午休、夜间安全、停车、行李、跨城移动和吃饭半径。推荐酒店时必须解释为什么。

## 何时使用

当用户询问住宿、酒店、住哪里、订哪家、酒店区域，或完整攻略包包含住宿安排时，读取本文件。

## 输出要求

不要只输出“推荐 A/B/C”。至少包含：

1. 住宿策略
   说明本次旅行为什么适合住某个区域或某类酒店。把它和旅行主题、每日路线、夜间活动、交通方式、同行人状态连接起来。

2. 候选对比表
   至少对比 2-5 个候选。每个候选写清：
   - 推荐结论：首选、备选、只适合某类人、不建议
   - 适合主题：例如古城慢逛、夜生活、安全收尾、亲子省力、自驾停车、海边度假
   - 位置逻辑：离主路线、餐厅、酒吧、车站、机场、停车点或景点的关系
   - 体验逻辑：空间、设计、服务、安静度、景观、当地生活感或仪式感
   - 实用逻辑：房型、床型、早餐、行李、停车、电梯、洗衣、取消政策
   - 风险：价格、噪音、房间小、交通不便、夜间回程、订不到、评价两极
   - 复核点：官网/订房平台、近期评价、地图距离、停车政策、入住退房时间

3. 为什么选最终方案
   如果给出最终推荐，必须解释它相对其他候选赢在哪里，以及它牺牲了什么。

4. 为什么不选其他方案
   对被淘汰或降级的酒店说明具体原因，不要只说“不如首选”。

5. 路线影响
   说明酒店选择会如何改变每日路线、晚餐/酒吧半径、午休可能性和移动日安排。

## 推荐格式

```text
住宿策略：
这趟更适合住在 X 区域，因为它能服务 A 主题、B 动线和 C 安全/交通需求。相对 Y 区域，它牺牲的是什么。

酒店候选对比：
| 酒店 | 结论 | 为什么适合 | 主要风险 | 适合的路线/主题 |
| --- | --- | --- | --- | --- |
| A | 首选 | ... | ... | ... |
| B | 备选 | ... | ... | ... |
| C | 不建议/特殊情况可选 | ... | ... | ... |

最终选择理由：
选择 A，不是因为它单项最强，而是因为它在位置、晚间安全、房型、价格和路线衔接之间最平衡。

为什么不选其他候选：
- 候选二：...
- 候选三：...

对行程的影响：
- Day 1：...
- Day 2：...
```

## 判断维度

按任务需要选择维度，不要机械堆满：

- 路线锚点：是否方便每天出发和回到酒店
- 晚间安全：酒吧、夜游、晚餐后回程是否安全
- 交通：机场、车站、地铁、公交、自驾出城是否顺
- 停车：是否有停车、是否能开到门口、取车是否方便
- 行李：寄存、搬运行李、楼梯、电梯、退房后安排
- 房型：多人、亲子、双床、大床、连通房、加床
- 休息：是否适合午休、是否安静、是否减少通勤消耗
- 吃喝半径：附近是否有保底餐、咖啡、早餐、夜宵
- 主题匹配：是否服务本次主题，而不是只看评分
- 预算：总价、税费、取消政策、性价比和溢价是否合理

## 避免

- 只按平台评分排序。
- 只给酒店名字，不解释取舍。
- 只写优点，不写风险。
- 不说明酒店对每日路线的影响。
- 忽略同行人数、床型、行李、停车和夜间回程。
